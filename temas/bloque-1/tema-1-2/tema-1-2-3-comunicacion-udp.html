EXPLORA

UDP envía datagramas independientes

La aplicación decide qué enviar y a qué destino. UDP no establece una conexión previa ni confirma automáticamente la recepción.

Socket

SOCK_DGRAM

Indica que el socket utilizará semántica de datagramas.

  • Cada envío mantiene sus límites.
  • No crea un flujo continuo de bytes.
Destino

sendto()

Envía un datagrama e incluye explícitamente el extremo de destino.

  • Recibe bytes.
  • Recibe la tupla IP y puerto.
Origen

recvfrom()

Recibe un datagrama y devuelve tanto los bytes como la dirección del emisor.

  • Conserva el mensaje recibido.
  • Permite responder al origen.
Servidor UDP

bind()

Asocia el receptor a una dirección local y un puerto conocido.

  • No se usan listen() ni accept().
  • El socket puede recibir de distintos emisores.

TCP 1.2.2

  • Orientado a conexión.
  • Usa un flujo de bytes.
  • Incluye mecanismos de entrega ordenada y retransmisión.
  • Servidor típico: bind → listen → accept.

UDP 1.2.3

  • No requiere conexión previa.
  • Trabaja con datagramas.
  • No garantiza entrega, orden ni ausencia de duplicados.
  • Receptor típico: bind → recvfrom.
Precisión importante: decir “UDP no tiene conexión” no significa “UDP no usa direcciones”. Cada datagrama debe poder llegar a un destino identificado por IP y puerto. En Python, sendto() permite indicar ese destino en cada envío.

EXPLICA CON CÓDIGO

Un emisor y un receptor UDP mínimos

Observa la ausencia de listen(), accept() y connect() en este modelo básico.

Receptor UDP

import socket HOST = "127.0.0.1" PORT = 5001 with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as server: server.bind((HOST, PORT)) print("UDP esperando datagramas...") data, addr = server.recvfrom(2048) print("Desde:", addr) print("Recibido:", data.decode()) server.sendto(b"ACK UDP", addr)

Lectura: recvfrom() entrega el contenido y la dirección del emisor. Esa dirección puede reutilizarse para responder.

Emisor UDP

import socket HOST = "127.0.0.1" PORT = 5001 with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as client: destino = (HOST, PORT) client.sendto(b"RSSI=-67 dBm", destino) data, addr = client.recvfrom(2048) print("Respuesta de", addr) print(data.decode())

Lectura: el destino se especifica en sendto(). El cliente no crea una sesión TCP antes de enviar.

EJERCICIO RESUELTO

Telemetría simple de potencia recibida

Un equipo remoto debe enviar periódicamente una lectura corta a un recolector de un NOC. Por ahora solo necesitamos una demostración básica con un datagrama.

Situación
El recolector escucha en 192.168.10.20:6000. El equipo remoto debe enviar el texto RX=-18.5 dBm.
1
Elegir el tipo de socket.
Como el ejercicio exige UDP sobre IPv4, usamos socket.AF_INET y socket.SOCK_DGRAM.
2
Publicar el recolector.
El receptor ejecuta bind(("192.168.10.20", 6000)) para asociarse con el extremo conocido.
3
Convertir el mensaje a bytes.
"RX=-18.5 dBm".encode("utf-8") produce los bytes que requiere la API de sockets.
4
Enviar el datagrama.
El emisor ejecuta sendto(datos, ("192.168.10.20", 6000)).
5
Identificar al origen.
El receptor usa datos, origen = recvfrom(2048); así puede conocer quién envió la lectura.
Interpretación: el código básico permite transportar una lectura, pero todavía no resuelve pérdida, autenticación, validación del formato ni reintentos. Esas necesidades dependen de la aplicación y se tratarán progresivamente.

Lectura profesional

UDP puede ser adecuado cuando la aplicación tolera pérdidas puntuales y valora mensajes breves, frecuentes e independientes. Sin embargo, la elección no debe basarse únicamente en la palabra “rápido”.

  • ¿Qué ocurre si varias lecturas consecutivas se pierden?
  • ¿Necesitas detectar sensores inactivos?
  • ¿Debes validar que el datagrama provenga de un origen autorizado?
  • ¿La aplicación necesita confirmaciones o numeración de secuencia?
Ingeniería: el transporte es solo una parte del diseño. El protocolo de aplicación debe definir formato, significado, validación y respuesta ante fallos.
