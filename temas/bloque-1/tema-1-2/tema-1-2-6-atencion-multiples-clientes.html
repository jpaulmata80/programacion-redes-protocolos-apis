Atención básica de múltiples clientes

Un servidor real rara vez recibe una sola conexión. En este subtema compararás un servidor secuencial con un modelo concurrente básico y aprenderás a delegar cada conexión TCP a un hilo de atención.

Cómo trabajar este tema

Primero comprende el problema; después añade concurrencia

No se trata de “poner hilos” por costumbre. La pregunta es qué ocurre cuando una conexión tarda y existen otros clientes esperando servicio.

1. Distinguir servidor secuencial y servidor concurrente básico.
2. Interpretar el papel del socket de escucha y del socket conectado.
3. Implementar una estrategia básica de un hilo por cliente.
4. Justificar cuándo esta solución es suficiente y cuándo deja de escalar.
Alcance. Usaremos threading como primera estrategia didáctica de concurrencia. No entraremos todavía en asyncio, pools de trabajadores, multiproceso ni arquitecturas de alta escala.
Explora

¿Qué cambia cuando llegan varios clientes?

El socket de escucha sigue aceptando conexiones. Lo que cambia es qué hacemos con cada socket conectado después de accept().

Secuencial

Uno después de otro

El servidor acepta un cliente, lo atiende completamente y recién después vuelve a aceptar o atender al siguiente.

Concurrente

Atenciones solapadas

El servidor puede mantener varias conexiones activas y avanzar con más de una atención durante el mismo intervalo.

Hilo

Una función de atención

Una estrategia inicial consiste en ejecutar la función que atiende al cliente dentro de un hilo independiente.

Límite

No escala indefinidamente

Crear un hilo por cliente simplifica el aprendizaje, pero cada hilo consume recursos. Para alta escala existen otros modelos.

Concurrencia no significa necesariamente paralelismo. En este contexto importa que una conexión que está esperando E/S de red no impida que el servidor progrese con otras conexiones.

Explica

Una primera implementación con threading

La idea clave es separar el bucle que acepta conexiones de la función que conversa con cada cliente.

Servidor secuencial

import socket with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as server: server.bind(("0.0.0.0", 5000)) server.listen() while True: conn, addr = server.accept() with conn: data = conn.recv(1024) conn.sendall(b"OK")

Mientras el bloque de atención no termine, el flujo principal no vuelve a ejecutar accept().

Servidor con un hilo por cliente

import socket import threading def atender_cliente(conn, addr): with conn: data = conn.recv(1024) conn.sendall(b"OK") with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as server: server.bind(("0.0.0.0", 5000)) server.listen() while True: conn, addr = server.accept() hilo = threading.Thread( target=atender_cliente, args=(conn, addr), daemon=True ) hilo.start()

El hilo principal vuelve rápidamente a accept(), mientras otro hilo atiende la conexión aceptada.

Detalle importante: el socket server escucha nuevas conexiones; conn representa una conexión concreta con un cliente. No deben confundirse.
Ejercicio resuelto

Servidor de consulta para tres técnicos de campo

Un servidor TCP recibe consultas que pueden tardar varios segundos porque debe obtener el estado de un equipo remoto.

Problema

Tres técnicos consultan casi al mismo tiempo

¿Qué modificación mínima permite que una consulta lenta no obligue a esperar a todas las demás?

1
Identificar el cuello de botella.
En el servidor secuencial, la atención completa ocurre dentro del mismo flujo que acepta nuevas conexiones.
2
Separar responsabilidades.
El bucle principal conserva accept(); la lógica de conversación se mueve a atender_cliente().
3
Delegar la conexión.
Después de cada accept(), se crea un hilo cuyo argumento es el socket conectado conn.
4
Cerrar correctamente.
Cada función de atención administra su propio conn mediante with conn:.
5
Reconocer el límite.
La estrategia es apropiada para una práctica y cargas pequeñas/moderadas, pero no implica que debamos crear hilos sin límite en un sistema de alta escala.
