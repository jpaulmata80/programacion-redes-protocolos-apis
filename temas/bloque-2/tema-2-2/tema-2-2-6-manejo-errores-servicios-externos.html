Manejo de errores y respuestas de servicios externos

Diseña clientes que sigan siendo útiles cuando una API tarda, rechaza una solicitud, limita la frecuencia o falla temporalmente.

Comenzar recorrido Volver al Tema 2.2

No todos los fallos significan lo mismo

Timeout
No respondió a tiempono prueba por sí solo que el servicio esté caído
Conexión
No se pudo establecer/completar la comunicaciónDNS, TCP, TLS o conectividad pueden intervenir
4xx

5xx

429

Cómo trabajar este tema

Primero clasifica el fallo; después decide

Reintentar todo de la misma manera puede empeorar un problema. La respuesta correcta depende del tipo de error y de la operación que intentabas realizar.

1. Diferenciar errores de red y respuestas HTTP no exitosas.
2. Manejar excepciones frecuentes de requests.
3. Decidir cuándo un reintento puede ser razonable.
4. Diseñar una respuesta degradada para una aplicación de red.
Alcance. Se introducen estrategias básicas de robustez. No se desarrollarán circuit breakers, colas distribuidas, alta disponibilidad avanzada ni bibliotecas especializadas de resiliencia.
Explora

Error de red y error HTTP no son lo mismo

Si recibes un código HTTP, el intercambio llegó lo suficientemente lejos como para obtener una respuesta del servicio o de un intermediario.

Timeout

Espera agotada

La operación no recibió a tiempo lo esperado. Es evidencia de no respuesta dentro del límite configurado, no prueba absoluta de caída total.

ConnectionError

Problema de conexión

Puede deberse a DNS, rechazo de conexión, interrupciones de red u otros fallos de conectividad.

4xx / 5xx

Respuesta HTTP

El servidor o intermediario sí devolvió una respuesta que debe interpretarse según su código.

Reintento

Decisión controlada

No debe ser automático para todo. Considera código, método, idempotencia, límites y documentación.

Idempotencia importa. Reintentar un GET suele ser conceptualmente menos riesgoso que repetir un POST que podría crear un recurso duplicado. La decisión final depende del contrato real del servicio.

Explica

Patrones básicos de manejo de fallos

El código debe distinguir entre ausencia de respuesta, respuesta HTTP no exitosa y errores inesperados.

Clasificar excepciones

import requests try: respuesta = requests.get( url, timeout=5 ) respuesta.raise_for_status() except requests.Timeout: print("Timeout") except requests.ConnectionError: print("Error de conexión") except requests.HTTPError as exc: print( "Error HTTP:", exc.response.status_code ) except requests.RequestException as exc: print("Fallo de solicitud:", exc)

Capturar primero excepciones específicas hace más clara la reacción del programa.

Reintento limitado

import time import requests for intento in range(3): try: r = requests.get( url, timeout=5 ) r.raise_for_status() break except requests.Timeout: if intento == 2: raise time.sleep(2 ** intento)

Este patrón didáctico usa retroceso progresivo simple. En producción conviene respetar la política concreta de la API.

Tratar 429

if respuesta.status_code == 429: espera = respuesta.headers.get( "Retry-After" ) print( "Límite alcanzado.", "Retry-After:", espera )

Retry-After puede orientar la espera cuando el servicio lo proporciona.

Degradación controlada

try: r = requests.get( url, timeout=5 ) r.raise_for_status() datos = r.json() except requests.RequestException: datos = None if datos is None: print( "Inventario temporalmente no disponible" )

Una función secundaria puede fallar sin obligar a terminar toda la aplicación.

No reintentes sin límite. Un bucle agresivo puede aumentar la carga del servicio, empeorar una incidencia o provocar bloqueos por rate limiting.
Ejercicio resuelto

Consulta de inventario con degradación

Una aplicación del NOC consulta una API de inventario para enriquecer alarmas, pero la alarma debe seguir mostrándose aunque la API externa falle.

Problema

Evitar que un servicio secundario bloquee el flujo principal

1
Definir timeout.
No esperar indefinidamente por inventario.
2
Capturar fallos.
Distinguir timeout/conexión de errores HTTP.
3
Conservar flujo principal.
Mostrar la alarma aunque falten datos adicionales.
4
Registrar contexto.
Guardar tipo de fallo sin registrar secretos.
5
Reintentar solo si corresponde.
Con límite y espera controlada.
import requests def obtener_inventario(equipo_id): url = ( "https://api.example" f"/v1/equipos/{equipo_id}" ) try: r = requests.get( url, timeout=5 ) r.raise_for_status() return r.json() except requests.RequestException: return None inventario = obtener_inventario(452) if inventario is None: print( "Alarma recibida; " "inventario no disponible" ) else: print( "Alarma enriquecida con inventario" )
