Cómo trabajar este tema

Un log útil debe responder preguntas operativas

¿Qué operación ocurrió? ¿Sobre qué recurso? ¿Cuál fue el resultado? ¿Cuánto tardó? ¿Qué dependencia falló?

1. Registrar eventos con niveles de severidad coherentes.
2. Añadir contexto útil sin incluir secretos.
3. Medir tiempos y estados básicos de operación.
4. Diferenciar logging, monitoreo y diagnóstico.
Alcance. Trabajaremos observabilidad básica dentro de la aplicación. Plataformas profesionales de métricas, trazas distribuidas, alertamiento y centralización de logs quedan fuera de este subtema.
Explora

Logs y monitoreo se complementan, pero no son lo mismo

Los logs registran eventos concretos; el monitoreo observa el comportamiento del sistema a lo largo del tiempo mediante estados e indicadores.

INFO

Operación normal

Inicio de servicio, tarea completada o consulta realizada correctamente.

WARNING

Degradación

La operación continúa, pero existe una condición anómala o una dependencia secundaria no disponible.

ERROR

Fallo relevante

Una operación esperada no pudo completarse y requiere diagnóstico.

Monitoreo

Estado e indicadores

Disponibilidad básica, duración de operaciones, número de errores u otros indicadores definidos.

EventoNivel sugeridoContexto útilNo registrar

La severidad representa impacto, no dramatismo. Un ERROR debe indicar que una operación importante falló; no todo evento inesperado necesita el nivel más alto.

Explica

Logging y monitoreo básico con Python

La biblioteca estándar permite comenzar con registros consistentes sin depender de herramientas externas.

Configurar logging

import logging logging.basicConfig( level=logging.INFO, format=( "%(asctime)s " "%(levelname)s " "%(name)s " "%(message)s" ) ) logger = logging.getLogger( "app.red" )

El timestamp, nivel y nombre del logger ayudan a interpretar cada evento.

Registrar una operación

logger.info( "consulta_inventario " "equipo_id=%s status=%s", equipo_id, response.status_code )

Usa parámetros de logging en lugar de construir mensajes sensibles innecesarios.

Medir duración

from time import perf_counter inicio = perf_counter() resultado = consultar_inventario( equipo_id ) duracion_ms = round( (perf_counter() - inicio) * 1000, 1 ) logger.info( "inventario_fin " "equipo_id=%s duracion_ms=%s", equipo_id, duracion_ms )

perf_counter() es apropiado para medir duraciones dentro del proceso.

Registrar degradación

if inventario is None: logger.warning( "inventario_no_disponible " "equipo_id=%s", equipo_id ) return { "equipo_id": equipo_id, "inventario": "no disponible" }

WARNING comunica una degradación cuando la aplicación todavía puede entregar un resultado útil.

Registrar una excepción

try: ejecutar_diagnostico( equipo_id ) except ErrorDiagnostico: logger.exception( "diagnostico_fallido " "equipo_id=%s", equipo_id ) raise

logger.exception() incluye información de la excepción cuando se usa dentro de un bloque except.

Estado básico de la aplicación

@app.get("/health") def health(): return { "status": "ok" }

Un endpoint de salud básico confirma que la aplicación responde; por sí solo no demuestra que todas sus dependencias estén sanas.

No confundas health con disponibilidad completa. Que /health responda 200 puede significar únicamente que el proceso está activo. La salud de bases de datos, APIs externas u otros componentes debe evaluarse según el diseño de la aplicación.

Problema

Registrar lo necesario para diagnosticar sin revelar secretos

1
Inicio.
Registrar identificador de equipo y operación.
2
Duración.
Medir tiempo con perf_counter().
3
Resultado.
Registrar status o tipo de fallo.
4
Severidad.
INFO para éxito, WARNING para degradación, ERROR para operación fallida.
5
Seguridad.
No registrar Authorization, contraseñas ni tokens.
Ejemplo útil: WARNING inventario_no_disponible equipo_id=452 duracion_ms=5002. Informa qué falló y cuánto tardó sin revelar la credencial utilizada.

Caso profesional

Diagnóstico operativo para un NOC

La aplicación procesa alarmas, consulta inventario y expone resultados. El equipo necesita investigar fallos sin revisar el código en tiempo real.

El objetivo es poder reconstruir lo ocurrido sin exponer secretos.

Reflexión

Diseña la observación de una aplicación

Elige una tarea de red y define qué eventos registrarías, qué contexto incluirías, qué medirías y qué información sensible excluirías.

Ideas clave

Los logs deben ser útiles, contextuales y seguros; el monitoreo complementa esos eventos con estados e indicadores del comportamiento de la aplicación.
