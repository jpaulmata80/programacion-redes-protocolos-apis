Cómo trabajar este tema

Probar una función no equivale a probar el servicio

Una prueba funcional observa la aplicación desde su interfaz: envía una solicitud y verifica el comportamiento que experimentaría un consumidor.

1. Diseñar escenarios funcionales de éxito y error.
2. Verificar status codes y estructura JSON.
3. Comprobar degradación ante dependencias no disponibles.
4. Mantener pruebas repetibles y aisladas de servicios reales cuando corresponda.
Alcance. Estas pruebas se centran en el comportamiento funcional del servicio. Pruebas de carga, rendimiento extremo, penetración y alta disponibilidad pertenecen a otros niveles de evaluación.
Explora

Una buena prueba funcional describe un escenario real

“Cuando ocurre X y el cliente hace Y, el servicio debe responder Z”.

Happy path

Flujo exitoso

Comprueba que una operación válida produce el resultado esperado.

Validación

Entrada inválida

Verifica que la aplicación rechace datos que incumplen el contrato.

Error

Recurso o dependencia

Comprueba respuestas como 404, 409 o degradación ante un servicio externo.

Repetibilidad

Resultado estable

La prueba debe poder ejecutarse nuevamente sin depender de cambios impredecibles de Internet o producción.

Las dependencias externas deben controlarse en pruebas. Si una prueba depende de una API real en Internet, puede fallar por causas ajenas al código. En pruebas repetibles conviene sustituir esa frontera por una respuesta conocida.

Explica

Pruebas funcionales con FastAPI TestClient

El cliente de pruebas permite ejecutar solicitudes contra la aplicación y comprobar el contrato sin abrir un puerto de red real.

Preparar TestClient

from fastapi.testclient import TestClient from main import app client = TestClient(app)

La prueba interactúa con la aplicación mediante HTTP simulado dentro del proceso.

Flujo exitoso

def test_diagnostico_ok(): response = client.get( "/api/diagnostico/452" ) assert response.status_code == 200 data = response.json() assert data["equipo_id"] == 452 assert "alcanzable" in data

No comprueba la implementación interna, sino el resultado observable.

Validación de entrada

def test_id_invalido(): response = client.get( "/api/diagnostico/abc" ) assert response.status_code == 422

El contrato debe rechazar un ID incompatible con el tipo esperado.

Recurso inexistente

def test_equipo_no_existe(): response = client.get( "/api/equipos/999" ) assert response.status_code == 404 assert "detail" in response.json()

Los errores esperados también forman parte de la funcionalidad.

Dependencia controlada

def inventario_no_disponible( equipo_id ): return None def test_diagnostico_degradado( monkeypatch ): monkeypatch.setattr( "main.obtener_inventario", inventario_no_disponible ) response = client.get( "/api/diagnostico/452" ) assert response.status_code == 200 assert response.json()[ "inventario" ] == "no disponible"

La prueba controla la frontera externa para verificar el comportamiento de degradación definido por la aplicación.

Ejecutar con pytest

python -m pytest -q

Las pruebas deben poder ejecutarse repetidamente y producir resultados claros.

No pruebes producción mediante efectos destructivos. Las pruebas funcionales deben usar datos y entornos controlados, especialmente para POST, PATCH y DELETE.

Problema

Comprobar que el servicio cumple su contrato

1
Éxito.
Equipo válido + inventario disponible → 200 y datos combinados.
2
Validación.
ID no entero → 422.
3
Ausencia.
Equipo inexistente → 404 según contrato.
4
Degradación.
Inventario falla → conservar dato de red y marcar inventario no disponible.
5
Repetibilidad.
La dependencia externa se sustituye por respuestas controladas durante la prueba.
Criterio: si una nueva versión rompe cualquiera de estos comportamientos sin que el contrato haya cambiado intencionalmente, la prueba debe detectarlo.
