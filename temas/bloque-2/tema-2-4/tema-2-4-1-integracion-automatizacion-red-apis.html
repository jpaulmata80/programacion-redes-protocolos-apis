Integración entre automatización de red y APIs

Conecta scripts de automatización, información de dispositivos, APIs propias y servicios externos para construir flujos operativos completos y reutilizables.

Cómo trabajar este tema

Integra componentes sin mezclarlos

Una aplicación sólida separa la obtención de datos de red, el acceso a APIs, la validación y la presentación del resultado.

1. Diseñar un flujo que combine automatización de red y APIs.
2. Separar responsabilidades entre adquisición, consulta, integración y salida.
3. Validar datos de distintas fuentes antes de combinarlos.
4. Mantener funcionalidad útil ante fallos parciales.
Diferencia respecto a 2.2.7: allí se integraba principalmente el consumo de una API con una aplicación. Aquí se conecta ese consumo con automatización de red y, cuando conviene, con una API propia que expone el resultado.
Explora

Una integración es una cadena de responsabilidades

Cada componente debe saber qué hace y qué entrega al siguiente.

Adquisición

Datos de red

El script puede obtener estado, latencia, interfaz, dirección IP o salida de un dispositivo.

Automatización

Acción programática

Una tarea repetitiva se encapsula en una función o módulo reutilizable.

API

Intercambio estructurado

Permite consultar información externa o exponer resultados internos a otras aplicaciones.

Integración

Dato enriquecido

El resultado combina fuentes distintas sin ocultar cuándo alguna información no estuvo disponible.

SalidaDashboard o API interna recibe resumen.
Regla clave: una API externa es una dependencia, no una fuente de verdad absoluta. Sus datos deben validarse y su indisponibilidad debe manejarse explícitamente.
Predice

¿Qué debería ocurrir ante un fallo parcial?

El script confirma que un equipo no responde, pero la API de inventario está temporalmente fuera de servicio.

Una integración robusta conserva la información válida que sí pudo obtenerse.

Explica

Separar adquisición, API e integración

Cada función tiene una responsabilidad y puede probarse de forma independiente.

1. Obtener dato de red

def obtener_estado_red(equipo_id): # En un entorno real: # ping, SSH, SNMP, socket, etc. return { "equipo_id": equipo_id, "alcanzable": False }

El ejemplo simula la adquisición para concentrarse en la arquitectura.

2. Consultar API

import requests def obtener_inventario(equipo_id): url = ( "https://api.example" f"/v1/equipos/{equipo_id}" ) try: r = requests.get( url, timeout=5 ) r.raise_for_status() datos = r.json() except requests.RequestException: return None if not isinstance(datos, dict): return None return datos

La función encapsula la dependencia externa.

3. Integrar datos

def construir_diagnostico( equipo_id ): red = obtener_estado_red( equipo_id ) inventario = obtener_inventario( equipo_id ) resultado = { "equipo_id": equipo_id, "alcanzable": red["alcanzable"] } if inventario: resultado["sitio"] = ( inventario.get("sitio") ) else: resultado["inventario"] = ( "no disponible" ) return resultado

La integración conserva el dato principal aunque falle la fuente secundaria.

4. Exponer mediante API propia

from fastapi import FastAPI app = FastAPI() @app.get( "/api/diagnostico/{equipo_id}" ) def diagnostico( equipo_id: int ): return construir_diagnostico( equipo_id )

El resultado de automatización puede convertirse en servicio para otros consumidores.

Evita acoplamiento excesivo: la función que consulta la red no debería conocer detalles de FastAPI, y el endpoint no debería contener toda la lógica de automatización.
Ejercicio resuelto

Diagnóstico enriquecido de un equipo

Un equipo no responde. La aplicación debe combinar estado técnico e inventario.

Problema

Construir un flujo operativo sin mezclar responsabilidades

1
Adquisición.
Obtener el estado del equipo desde la red.
2
Enriquecimiento.
Consultar inventario con el identificador del equipo.
3
Validación.
Comprobar que la respuesta externa tenga estructura utilizable.
4
Integración.
Combinar datos disponibles sin inventar campos faltantes.
5
Salida.
Entregar el resumen al dashboard o mediante una API interna.
Resultado esperado: “Equipo 452 no alcanzable; sitio AZG-01; responsable NOC-Sur”. Si el inventario falla: “Equipo 452 no alcanzable; inventario no disponible”.
