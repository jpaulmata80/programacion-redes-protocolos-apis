Cómo trabajar este tema

Un error bien manejado empieza por saber qué falló

No es lo mismo un timeout, un HTTP 404, un JSON inválido o una respuesta válida que no contiene los campos requeridos.

1. Validar entradas propias y respuestas externas.
2. Clasificar errores antes de decidir una acción.
3. Aplicar degradación controlada cuando corresponda.
4. Evitar ocultar fallos mediante valores inventados o éxitos falsos.
Perspectiva del tema: en 2.3.3 validamos datos dentro de una API y en 2.2.6 manejamos errores al consumir servicios. Aquí ambos conceptos se integran a nivel de aplicación completa.
Explora

Validar en cada frontera de confianza

Todo dato que cruza desde una fuente externa hacia tu lógica debe considerarse potencialmente incompleto, inválido o inesperado.

Entrada

Datos del cliente

Path, query y body deben cumplir tipos, estructura y reglas antes de procesarse.

Dependencia

Respuesta externa

Un 200 no garantiza JSON válido ni la presencia de campos requeridos por tu aplicación.

Error

Clasificación

Timeout, conexión, HTTP, decodificación y semántica requieren respuestas diferentes.

Estrategia

Degradación

Si una dependencia es complementaria, la aplicación puede conservar datos válidos y marcar lo faltante.

Explica

Controlar errores sin ocultarlos

El objetivo es preservar significado: saber qué falló, qué datos siguen siendo válidos y qué debe comunicarse.

Clasificar errores de requests

import requests def consultar(url): try: r = requests.get( url, timeout=5 ) r.raise_for_status() except requests.Timeout: return { "ok": False, "tipo": "timeout" } except requests.ConnectionError: return { "ok": False, "tipo": "conexion" } except requests.HTTPError as exc: return { "ok": False, "tipo": "http", "status": exc.response.status_code } return { "ok": True, "response": r }

Cada clase de error transmite información distinta.

Validar JSON y estructura

def validar_inventario(response): try: data = response.json() except requests.JSONDecodeError: return None if not isinstance(data, dict): return None campos = { "id", "sitio", "responsable" } if not campos.issubset(data): return None return data

JSON válido no implica que el esquema requerido esté completo.

Degradación controlada

def integrar(red, inventario): resultado = { "equipo_id": red["equipo_id"], "alcanzable": red["alcanzable"] } if inventario is None: resultado["inventario"] = ( "no disponible" ) return resultado resultado["sitio"] = ( inventario["sitio"] ) return resultado

La aplicación conserva el dato local y declara qué parte faltó.

No ocultar fallos inesperados

try: resultado = ejecutar_tarea() except ErrorEsperado as exc: manejar_error_esperado(exc) # Evita: # except Exception: # return {"ok": True}

Responder éxito cuando ocurrió un fallo destruye la confiabilidad del sistema.

Reintentos: solo deben aplicarse cuando la operación y la causa del fallo lo permiten. Un reintento automático no debe asumirse seguro para cualquier método o tarea.
Ejercicio resuelto

Diagnóstico con dependencia externa inestable

La red local responde, pero el inventario puede fallar o devolver datos incompletos.

Problema

Preservar datos válidos sin ocultar el fallo

1
Obtener dato local.
Reachability del equipo.
2
Consultar inventario.
Capturar timeout, conexión y HTTP.
3
Validar contenido.
Comprobar JSON, tipo y campos requeridos.
4
Integrar.
Si inventario falla, conservar reachability y marcar dependencia no disponible.
5
Informar.
No transformar el fallo en un éxito falso ni inventar datos.
Resultado: “Equipo 452 alcanzable=false; inventario=no disponible” es más confiable que fingir un sitio desconocido o descartar el dato de red válido.
