Códigos de estado HTTP

Interpreta cómo un servidor comunica el resultado de una solicitud: éxito, redirección, error del cliente, error del servidor u otra condición informativa.

Comenzar recorrido Volver al Tema 2.1

Primero identifica la familia

1xxInformación provisional sobre la solicitud.
2xxLa solicitud fue procesada satisfactoriamente.
3xxSe requiere una acción adicional o existe otra representación/ubicación relevante.
4xxLa solicitud presenta un problema atribuible al lado del cliente.
5xxEl servidor o una dependencia no pudo completar correctamente la solicitud.
Cómo trabajar este tema

El método expresa intención; el código expresa resultado

Una solicitud GET, POST o PATCH puede terminar con distintos códigos. El cliente debe interpretar el código antes de asumir que la operación funcionó.

1. Reconocer las cinco familias de códigos HTTP.
2. Interpretar códigos frecuentes en APIs.
3. Diferenciar problemas del cliente y del servidor.
4. Seleccionar respuestas coherentes para escenarios de Telecomunicaciones.
Alcance. Trabajaremos códigos frecuentes y su semántica general. Cabeceras, parámetros y metadatos adicionales se desarrollarán en 2.1.5.
Explora

Cinco familias para orientarse rápidamente

El primer dígito permite anticipar el tipo general de resultado.

1xx

Informativos

Indican que la comunicación continúa o que se ha recibido una etapa provisional.

2xx

Éxito

La solicitud fue aceptada y procesada de forma satisfactoria según el código concreto.

3xx

Redirección

El cliente puede necesitar seguir otra ubicación, reutilizar una representación o realizar una acción adicional.

4xx

Error del cliente

La solicitud tiene un problema como sintaxis, autenticación, autorización, recurso inexistente o exceso de solicitudes.

5xx

Error del servidor

El servidor recibió la solicitud pero no pudo completar correctamente la operación.

400Bad RequestLa solicitud es inválida o no puede interpretarse como se esperaba.JSON mal formado o campo requerido incorrecto.
401UnauthorizedFalta autenticación válida para acceder al recurso.Token ausente o no válido.
403ForbiddenEl servidor entiende la solicitud pero rechaza autorizarla.Usuario sin permiso para modificar un enlace.
404Not FoundNo se encontró el recurso solicitado.No existe el enlace 99.
409ConflictLa solicitud entra en conflicto con el estado actual del recurso.Intento de crear un identificador ya existente.
429Too Many RequestsSe excedió una política o límite de solicitudes.Cliente consulta demasiado rápido.
500Internal Server ErrorFallo interno inesperado.Excepción no controlada en la aplicación.
502Bad GatewayUn intermediario recibió una respuesta inválida de un servidor aguas arriba.Gateway no obtiene respuesta válida del backend.
503Service UnavailableServicio temporalmente no disponible.Mantenimiento o sobrecarga temporal.
504Gateway TimeoutUn intermediario agotó el tiempo esperando una respuesta aguas arriba.Proxy espera demasiado al backend.
401 vs 403. 401 se relaciona con la necesidad de autenticación válida. 403 indica que el servidor rechaza autorizar la operación, incluso aunque haya entendido la solicitud.

Observa y explica

Mismo recurso, resultados distintos

El método no determina por sí solo el código de respuesta.

Consulta exitosa

GET /api/enlaces/15 → 200 OK

El recurso existe y la operación puede completarse.

Recurso inexistente

GET /api/enlaces/99 → 404 Not Found

La estructura de la solicitud puede ser correcta, pero el recurso solicitado no existe.

Falta autenticación

GET /api/enlaces/15 → 401 Unauthorized

El recurso puede existir, pero el cliente no presentó autenticación válida.

Fallo temporal del servicio

GET /api/enlaces/15 → 503 Service Unavailable

El servidor indica que el servicio no puede atender temporalmente la solicitud.

Ejercicio resuelto

Interpretar respuestas de una API de monitoreo

Un script consulta varios recursos y recibe códigos diferentes.

Problema

Decidir qué significa cada respuesta

1
200.
La consulta fue procesada correctamente; el cliente puede interpretar el contenido recibido.
2
401.
El cliente debe revisar el mecanismo de autenticación o credenciales utilizadas.
3
404.
El recurso no fue encontrado; conviene revisar identificador o ruta.
4
429.
El cliente debe respetar la política de frecuencia y evitar insistir de forma agresiva.
5
503.
El servicio está temporalmente indisponible; una estrategia de reintento controlado puede ser apropiada según la aplicación.
Conclusión: el cliente no debe tratar todos los códigos distintos de 200 como el mismo error. Cada familia y código aporta contexto para decidir el siguiente paso.
