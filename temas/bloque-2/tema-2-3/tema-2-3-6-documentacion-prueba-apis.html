Documentación y prueba de APIs

Convierte el contrato de tu API en algo visible y verificable: documentación OpenAPI, interfaz interactiva, pruebas manuales y pruebas funcionales básicas.

Cómo trabajar este tema

Si otro desarrollador no puede entenderla ni comprobarla, la API aún no está lista

La documentación comunica el contrato; las pruebas verifican que la implementación respete ese contrato.

1. Interpretar la documentación OpenAPI generada por FastAPI.
2. Probar endpoints de manera manual y controlada.
3. Crear pruebas funcionales básicas con TestClient.
4. Verificar status codes, cuerpos JSON y errores esperados.
Alcance. Se trabajan pruebas funcionales básicas del contrato HTTP. Pruebas de carga, seguridad avanzada, integración continua y observabilidad completa quedan para etapas posteriores.
Explora

Documentar y probar son actividades diferentes

Una documentación correcta puede describir un endpoint que está roto; una prueba comprueba el comportamiento real.

OpenAPI

Contrato estructurado

FastAPI genera un esquema OpenAPI a partir de rutas, modelos, parámetros y metadatos.

/docs

Interfaz interactiva

Permite explorar endpoints y ejecutar solicitudes durante el desarrollo.

Manual

Prueba exploratoria

Ayuda a observar solicitudes, respuestas y errores mientras se desarrolla la API.

Automática

Prueba repetible

Comprueba de forma consistente el comportamiento esperado después de cambios.

Documentación automática no significa documentación completa. Los nombres de funciones, modelos, descripciones y códigos declarados deben ser claros para que el esquema generado sea realmente útil.

Explica

Documenta y prueba la API

FastAPI puede generar documentación útil y permite probar la aplicación sin levantar un servidor de red externo durante la prueba.

Metadatos de la aplicación

from fastapi import FastAPI app = FastAPI( title="API de Inventario de Red", description=( "Servicio para consultar y " "administrar equipos." ), version="1.0.0" )

Estos datos aparecen en la documentación generada.

Documentar un endpoint

@app.get( "/api/equipos/{equipo_id}", summary="Consultar equipo", description=( "Obtiene un equipo por " "su identificador." ) ) def obtener_equipo( equipo_id: int ): ...

Los nombres y descripciones deben ser comprensibles para el consumidor.

Prueba básica con TestClient

from fastapi.testclient import TestClient from main import app client = TestClient(app) def test_listar_equipos(): response = client.get( "/api/equipos" ) assert response.status_code == 200 assert "items" in response.json()

TestClient permite ejecutar solicitudes contra la aplicación dentro del proceso de prueba.

Probar 404

def test_equipo_no_existe(): response = client.get( "/api/equipos/999" ) assert response.status_code == 404 assert response.json()["detail"] == ( "Equipo no encontrado" )

También deben probarse errores esperados, no solo caminos exitosos.

Probar creación

def test_crear_equipo(): payload = { "nombre": "RTR-AZG-02", "estado": "up" } response = client.post( "/api/equipos", json=payload ) assert response.status_code == 201 assert response.json()["nombre"] == ( "RTR-AZG-02" )

La prueba valida tanto status code como datos relevantes de la respuesta.

Probar validación

def test_body_invalido(): payload = { "estado": "up" } response = client.post( "/api/equipos", json=payload ) assert response.status_code == 422

Una prueba negativa confirma que el contrato también rechaza entradas inválidas.

Dependencias: las pruebas con TestClient requieren las dependencias correspondientes del entorno de FastAPI. En un proyecto real conviene mantenerlas declaradas y reproducibles.
Ejercicio resuelto

Plan mínimo de pruebas para una API de enlaces

No basta con probar que “abre”. Debemos comprobar los escenarios centrales del contrato.

Problema

Diseñar pruebas para el CRUD básico

1
GET colección.
Esperar 200 y una lista/estructura de elementos.
2
GET individual válido.
Esperar 200 e ID correcto.
3
GET inexistente.
Esperar 404.
4
POST válido.
Esperar 201 y representación creada.
5
POST inválido.
Esperar rechazo por validación.
6
PATCH/DELETE.
Verificar modificación, eliminación y códigos previstos.
Buena práctica: una prueba debe ser específica y reproducible. “Lo probé una vez y funcionó” no equivale a tener una prueba automatizada.
