Cómo trabajar este tema

Diseña antes de implementar

El objetivo no es crear muchas rutas, sino una interfaz consistente que represente correctamente los recursos del dominio.

1. Modelar recursos y colecciones a partir de un problema de red.
2. Diseñar rutas para colecciones y recursos individuales.
3. Relacionar operaciones con métodos HTTP coherentes.
4. Justificar una estructura de API clara y consistente.
Alcance. Aquí se diseña el contrato. La implementación con un framework se realizará en 2.3.2.
Explora

Piensa en recursos, no en comandos

Una API orientada a recursos suele ser más consistente cuando las rutas representan entidades y los métodos expresan las operaciones.

Recurso

Entidad del dominio

Un enlace, estación, alarma o equipo que tiene identidad y datos asociados.

Colección

Conjunto de recursos

Por ejemplo /api/enlaces para representar el conjunto de enlaces disponibles.

Individual

Recurso concreto

Por ejemplo /api/enlaces/{id}. El nombre {id} es una convención de documentación/routing para un valor variable.

Query

Filtro u opción

Permite seleccionar o ajustar una consulta, por ejemplo ?estado=alerta.

Evita rutas basadas en verbos sin necesidad. En lugar de /obtenerEnlace/15 o /borrarEnlace/15, una interfaz orientada a recursos suele expresar la intención con el método HTTP sobre /enlaces/15.
No expongas la base de datos directamente. El diseño de una API debe representar el dominio y las necesidades del cliente; no tiene que copiar exactamente tablas, nombres internos o detalles de almacenamiento.

Observa y explica

Patrones de diseño que mejoran la consistencia

No son leyes universales, pero ayudan a que la interfaz sea fácil de aprender y mantener.

Nombres de recursos

/api/enlaces /api/estaciones /api/alarmas

Usa nombres comprensibles y consistentes. Evita mezclar estilos sin una razón documentada.

Colección e individual

/api/equipos /api/equipos/{id}

Mantener la misma raíz facilita interpretar qué representa cada ruta.

Filtrado

/api/alarmas?severidad=critica /api/enlaces?zona=sur

Los filtros pueden formar parte del query cuando la API los define de ese modo.

Relaciones

/api/estaciones/7/enlaces

Una ruta anidada puede expresar relación, pero un anidamiento excesivo vuelve la API difícil de mantener.

Versionado: si la API necesita versionarse, define una estrategia de forma consciente. Incluir /v1 en la ruta es una opción común, pero no una obligación universal.

Una buena API oculta detalles internos y expone un contrato comprensible.
