Cómo trabajar este tema

No devuelvas “algo”; devuelve una respuesta con significado

El cliente debe poder distinguir una consulta exitosa, un recurso inexistente, una entrada inválida y un fallo interno sin adivinar qué ocurrió.

1. Seleccionar códigos HTTP coherentes con el resultado.
2. Generar errores con HTTPException.
3. Evitar respuestas ambiguas como None ante errores del dominio.
4. Diferenciar errores esperados de fallos internos del servidor.
Alcance. Trabajaremos respuestas y excepciones del lado servidor. La documentación y prueba sistemática de la API se desarrollará en 2.3.6.
Explora

El código de estado forma parte del contrato

La representación JSON puede explicar el detalle, pero el código HTTP resume el resultado de la operación.

2xx

Éxito

200, 201 y 204 comunican distintos resultados exitosos.

4xx

Solicitud o recurso

El problema está relacionado con la solicitud, autenticación, autorización, recurso o conflicto.

5xx

Servidor

La aplicación o una dependencia no pudo completar correctamente la operación.

Exception

HTTPException

Permite interrumpir el endpoint y devolver un error HTTP explícito al cliente.

SituaciónCódigoInterpretación
Consulta exitosa200 OKLa operación se completó y se devuelve una representación.
Creación exitosa201 CreatedSe creó un nuevo recurso.
Eliminación sin cuerpo204 No ContentLa operación fue exitosa y no se devuelve representación.
Solicitud mal formada a nivel de negocio400 Bad RequestLa solicitud no puede procesarse tal como fue planteada.
Recurso inexistente404 Not FoundNo existe el recurso solicitado.
Conflicto409 ConflictLa operación entra en conflicto con el estado actual.
Validación automática422 Unprocessable EntityFastAPI no pudo validar la entrada contra el esquema.
Fallo inesperado500 Internal Server ErrorError no controlado del servidor.
No uses 500 para errores esperados del dominio. Si sabes que un recurso puede no existir, responde 404. Si sabes que puede existir un duplicado incompatible, considera 409. Un 500 representa un fallo interno inesperado.

Explica

Respuestas explícitas con FastAPI

El endpoint debe expresar tanto el éxito como los errores esperados.

404 con HTTPException

from fastapi import HTTPException @app.get("/api/equipos/{equipo_id}") def obtener_equipo( equipo_id: int ): for equipo in equipos: if equipo["id"] == equipo_id: return equipo raise HTTPException( status_code=404, detail="Equipo no encontrado" )

La función no continúa después de lanzar la excepción.

201 al crear

from fastapi import status @app.post( "/api/equipos", status_code=status.HTTP_201_CREATED ) def crear_equipo( equipo: EquipoEntrada ): nuevo = { "id": siguiente_id(), **equipo.model_dump() } equipos.append(nuevo) return nuevo

El código 201 comunica que la operación creó un recurso.

409 por conflicto

for equipo in equipos: if equipo["nombre"] == entrada.nombre: raise HTTPException( status_code=409, detail="El equipo ya existe" )

409 es útil cuando la operación entra en conflicto con el estado actual del recurso.

204 al eliminar

from fastapi import Response, status @app.delete( "/api/equipos/{equipo_id}", status_code=status.HTTP_204_NO_CONTENT ) def eliminar_equipo( equipo_id: int ): eliminar_por_id(equipo_id) return Response( status_code=204 )

Una respuesta 204 no debe incluir cuerpo de respuesta.

Errores inesperados: evita capturar todo con except Exception solo para devolver 200. Un fallo real debe quedar registrado y producir una respuesta de error apropiada.
